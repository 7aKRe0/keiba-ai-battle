  • 興味のある分野に取り組んで、自分の腕と知見を広げる。

確かめること(問い。2026-11-02 主催決定):

2. 使えるデータ

  • 学習・調整に使えるのは、11/8(日)までに確定したレースのデータだけ(凍結後はモデルに手を加えないため)。予想の入力には、評価期間中に確定したレースの結果(前走の着順・オッズなど)も、締切の時点で公開されていれば使ってよい。
  • 予想の入力には、締切の時点で手に入る情報なら何を使ってもよい(出馬表、天気予報、金曜時点の馬場状態、過去のレースのオッズ・人気など)。何を知っていて何を使うかの差も勝負のうち(2026-11-02 主催決定)。
  • ただし、次のものは使わない。問いの物差しを壊すため。
  • そのレースのオッズ・人気(使うと市場の予想をなぞることになり、市場との比較が意味を失う)。
  • 他人の予想(印など)。人や予想サービス(新聞・予想サイト・AI 予想サービスなど)が出した予想のこと。自分で組んだ仕組みの中の LLM の出力は含まない。
  • 外から取ってくるもの(出馬表、天気、外部 API や LLM の返事など)は、締切前にファイルに保存して「入力ファイル」とする。凍結したコマンドは入力ファイルだけを読む(作り直しの確認ができるようにするため)。
  • 予想に LLM を使ってよい(ローカル・クラウドとも)。ただし、予想を出すときの LLM には Web 検索をさせず、入力ファイルだけを渡す。LLM の返事も入力ファイルとして保存する(作り直しの確認で、計算の揺れによる不一致を避けるため)。
  • 締切後の騎手変更・斤量変更は予想に反映しない。
  • データの取り方は自由。JRA-VAN Data Lab の 1 か月無料お試し(1 回限り)を使う場合は、11/29 まで届くように申し込む日に注意する。

3. モデル凍結(11/11 23:59)

  • 凍結するもの: 予測コード(出馬表の取得・加工を含む)、学習済みモデル、11/8 までの成績データの写し、ライブラリの版の一覧、開発ログ。
  • 予測は決まったコマンド 1 つで出す(例: python predict.py <入力ファイルのフォルダ>)。入力ファイル以外の引数・設定の切り替えは受け付けない作りにし、乱数の種を固定する。入力ファイルを取ってきて保存するコードも凍結に含める。
  • 凍結するファイル一式のハッシュの一覧を作り、締切前に共有リポジトリに push する。主催エージェントは、GitHub に記録された push の時刻を取得して記録する。一覧には OpenTimestamps の時刻証明を付ける。
  • これ以降、凍結したものに手を加えない。評価期間にやるのは、入力ファイルを取ってきて、凍結したコマンドで予測を出すことだけ。

4. 予想の提出(各開催日の前日 21:00 締切)

  • その日の入力ファイルを保存し、凍結したコマンドで、その日の全レースの CSV を 1 本出す。
  • 締切までに、CSV と入力ファイル全部のハッシュを書いたファイル(hashes/YYYYMMDD_名前.txt)を共有リポジトリに push する。ハッシュだけなので、相手に予想の中身は見えない。締切前の最後の push を正式な提出とし、主催エージェントが GitHub に記録された push の時刻を取得して記録する。
  • CSV と入力ファイルは締切後に共有リポジトリに push する。ハッシュが提出したものと一致しなければ、その日の提出は無効。
  • その日の 2 人のハッシュのファイルに、OpenTimestamps の時刻証明を 1 回付ける。時刻証明が示すのは「発走前に存在したこと」までで、分単位の締切の証明には使わない(締切は GitHub の push の時刻で判定する)。
  • 形式: UTF-8、見出し行 race_id,馬番,確率。race_id は YYYYMMDD-場名-R(例: 20261114-東京-11)。ファイル名は YYYYMMDD_名前.csv。
  • 作り直しの確認: 主催エージェントが、凍結したコードとデータに提出した入力ファイルを入れて全開催日の CSV を作り直す。あわせて、入力ファイルにそのレースのオッズ・人気が含まれていないかを確かめる。全馬の確率の差が 0.000001 以内なら一致とする。一致しない日は、その日の提出を全馬同じ確率で採点する。
  • 出し忘れ・無効: 主催エージェントが凍結したコードで作り直した CSV で採点する。作り直せないときは全馬同じ確率で採点する。

5. 採点

  • 対象: 評価期間の全レース。レースの中止・開催の中止は採点から外す(平均の分母からも外す)。代替競馬は対象外。
  • 着順は確定着順(降着・失格を反映)。出走取消・発走除外の馬は外す。競走中止の馬は残す。
  • 処理の順番: 取消・除外の馬を外す → CSV に無い出走馬に 0.001 を付ける → 合計が 1 になるように直す → 勝った馬の確率 p を取る(同着は足す) → p が 0.001 未満なら 0.001 にする。
  • log loss: 全レースの −ln(p) の平均。小さい方が勝ち。 勝敗は平均の大小で決める。
  • 差の 95% 区間を、レース単位のペアのブートストラップ(10,000 回、乱数の種を固定)で出して並べる。区間が 0 をまたぐときも勝敗は平均で決め、報告書に「偶然と区別できない差」と書く。
  • 物差し:
  • 全馬同じ確率: 1 ÷ 出走頭数。
  • 市場の予想: JRA 公式の最終単勝オッズから、1/オッズ を出走馬で足して 1 に直したもの。最終オッズは締切後の情報(馬体重・馬場など)を含むので、同じ条件の相手ではなく「上限の目安」として扱う。
  • 問いへの答え: 到達率 =(全馬同じ確率の log loss − モデルの log loss)÷(全馬同じ確率の log loss − 市場の log loss)。0 なら何も考えない予想と同じ、1 なら市場と同じ。ブートストラップの区間つきで報告する。
  • 結果とオッズの正本は JRA 公式の成績ページ。結果パックには race_id・1 着の馬番・最終単勝オッズと出典のリンクだけを入れる(JRA-VAN のデータは配り直さない)。

6. おまけ: 人間代表との 1 レース

  • 対象レースと予備のレース(中止のとき用)を、11/11 までに決めて記録する。8 頭以上のレースから選ぶ。
  • モデルの印は、提出した CSV の確率の上位 3 頭(◎○▲ の順)。確率が同じなら馬番の若い方。
  • 人間代表は、発走前までに印を出す。何を見てもよい(エンタメ枠のため)。
  • 点数: ◎ が 1 着なら 3 点。さらに、印の馬(◎ を含む)が 3 着以内に入るごとに 1 点。例: ◎ が 1 着、▲ が 3 着 → 3 + 1 + 1 = 5 点。同点なら馬券の収支で決める。
  • 馬券: 3 者とも ◎ の単勝と複勝を 100 円ずつ。主催と友人がまとめて買う。◎ が取消・除外になったら、その馬券は返還扱いにして、印は繰り上げる。
  • 1 レースなので、問いへの答えには使わない。

5-1. 先に決めること(Q-01〜06)

既定は、案を作った側が置いた答えです。主催の決定ではありません。

Q-01 共通の入力が 18:00 までに置かれなかった日

  • 既定: その日の締切を「置いた時刻の 3 時間後」に延ばす(遅くとも開催日 3:00)。開催日 0:00 までに無ければ、2 人ともその日を採点から外し、理由と件数を記録する。
  • 注意: 既定でも、主催が置かないことでその日を落とせる(記録には残る)。
  • 別の形 (a): 延ばさない。自前の入力で出してよい。出せなければ全馬同じ確率(共通の入力に頼る人は出せない)。
  • 別の形 (b): 延ばさない。2 人ともその日を外す(自前で出した人の有効な日も消える)。

Q-02 共通の入力に出馬表以外を足すか

  • 既定: (1) 評価期間中に確定した着順(オッズ無し)を、主催が開催日の翌日に置く(目標。遅れても提出の有効性に影響しない)。(2) 各馬の近走は入れない。
  • (2) を入れると、各自の金曜の負担は減るが、主催が数百ページを取る工程が増える。

Q-03 作り直しを誰がやるか

  • 既定: 主催エージェント(主催の PC)が行う。凍結物は 11/28 21:00 の後〜11/30 に非公開の release へ置く。環境がそろわないときだけ、参加者が自分の PC で道具を動かして出力と環境を push する。
  • 別の形: 最初から各自が自分の PC で作り直して push する。受け渡し・環境差・JRA-VAN の再配布の問題は消えるが、「凍結したモデルの出力であること」が自己申告寄りになる。

Q-04 罰(1 レースあたり 0.1 を log loss に足す)を入れるか

  • 既定: 入れる。範囲は「作り直せない日」と「凍結の一覧なし」だけ。不一致・混入・形式の誤りには足さない。罰は 2 人の勝敗にだけ使い、到達率と問いへの答えは罰なしで出して両方載せる。
  • 入れる理由: 凍結したモデルが全馬同じ確率より悪いと分かった人は、出さなければ全馬同じ確率になり、出すより得になる。
  • 入れない理由: 締切後の push を発走前に限った(C-21)ので、結果を見てから取り下げる道は閉じている。正直な出し忘れにも当たる(LLM を使う人は共通の入力だけでは作り直せないので、出し忘れると必ず罰になる)。
  • 値 0.1 は例。全馬同じ確率と市場の差の半分くらい(実測して決めてよい)。

Q-05 作り直しの確認でのオッズ・人気の判定

  • 既定: そのレースのオッズの倍率・人気順位の数字が入力ファイルにあれば、出どころ(LLM の返事を含む)を問わず使ったとみなす。そのレースのものかは、その race_id・馬名と同じ行(同じ表)にある数字で見分け、判断と根拠を裁定に書く。見つかった日はその日を全馬同じ確率(罰なし)。LLM の返事に数字を書かせない作りは勧めにとどめる。
  • 別の形: LLM が自分で書いた言葉(「人気になりそう」など)は対象外。機械で区別できず、主催が読んで判断する範囲が広がる。

C-25(作り直しの確認・オッズ・人気の確認) 案: 作り直しは、凍結の一覧にあるファイルと入力ファイルだけを置いた空のフォルダで、申告した環境で行う。Python とライブラリは、凍結した版の一覧と環境の申告にしたがって主催が入れる。一覧に無いコード・モデル・データが要って動かなければ作り直せない扱い。主催側で環境がそろわないときは、その参加者が自分の PC で同じ道具を動かし、出力と環境を 記録/ に push する。一致しない日は全馬同じ確率で採点する(罰なし)。共通の入力に原因がある不一致は、参加者の不利にしない。
オッズ・人気の確認: 入力ファイルにそのレースのオッズ・人気の数字(倍率・人気の順位)が入っていないかを確かめる。出どころ(LLM の返事を含む)は問わない。そのレースのものかは、その race_id・馬名と同じ行(同じ表)にある倍率・順位の数字で見分け、判断と根拠を裁定に書く。入っていた日は、その日の提出を全馬同じ確率で採点する(罰なし)。

C-27(出し忘れ・無効、罰) 案: 出し忘れ・無効のときは、主催エージェントが、凍結したコードと、締切までに置かれた共通の入力だけで作り直した CSV で採点する。参加者が後から出した入力ファイルは使わない。作り直せないときは全馬同じ確率で採点する。出し忘れは記録し、件数を報告書に書く。
罰: 作り直せなくて日全体を全馬同じ確率で採点する場合と、凍結の一覧が無い場合は、1 レースあたり 0.1 を log loss に足す。作り直しの不一致・オッズや人気の混入・形式の誤りには足さない。罰は 2 人の勝敗にだけ使う。到達率と問いへの答えは罰なしの log loss で出し、罰の有無を両方載せる。
理由: 今の文だと「わざと無効にして締切後の入力で作り直させる」道と「出さない方が得」の道が残る(Q-04)。

C-28(形式の誤り。新設) 案: 形式の誤りは直さない。CSV に無いレースと、形式の違う行(数でない・負・空・同じ馬が 2 行)を含むレースは、そのレースだけ全馬同じ確率で採点する(日全体は無効にしない)。見出し行・ファイル名・文字コードの誤りは、その日を全馬同じ確率で採点する(罰なし)。
理由: 今の採点スクリプトは、おかしな 1 行で全体が止まる。スクリプトの直しは 11/6 の予行が期限で、直せなければこの文を今の動きに合わせる。

理由: 採点スクリプトだけが決めていたことをルールに書く。

C-31(5 節 物差しの後) 案: 全頭の最終単勝オッズが取れなかったレースは、3 つとも採点から外し、件数を報告書に書く(中止と同じ扱い)。
理由: JRA 公式から自動で取れるかは未確認。欠けたレースで分母が崩れないように。

C-32(5 節 結果の正本) 案: 結果/結果.csv(1 行 1 レース、race_id,1着,取消除外,単勝オッズ,出典)は、保存したページ(結果/原本/)からスクリプトで作り、転記はしない。スクリプトで作れないレースは、2 人がそれぞれ同じ原本から作って突き合わせ、違いがあれば記録する。保存したページとスクリプトは共有リポジトリに置き、2 人とも同じ出力が出ることを確かめられるようにする。件数は 1 節の表と突き合わせる。
理由: 転記で 1 着が 1 つ違えば点数が変わる。スクリプトは未作成。

C-33(6 節) 案: 足す「取消・除外で 7 頭以下になったときは予備に替える。予備も 7 頭以下なら、そのまま行い複勝は 2 着まで。」「人間代表の印は push の時刻で確かめる。発走前に無ければ不参加とする。」
理由: 頭数が減ったときと、印が遅れたときの扱いが無かった。

C-34(7 節) 案: 経験に「11/4 より前から持っているコード・データ・モデルの種類と量」を足す。1 行は「AI に頼んだ 1 つのまとまり」(同じ試行の繰り返しは 1 行にまとめて回数を書く)。毎日の push は目標(遅れても凍結までにそろえばよい)。凍結後の AI の利用(入力の取得・提出の運用・手で入力ファイルを直したこと)は、凍結の一覧の外の 開発ログ_評価期間_名前.md に日ごとの合計と 1 行の注記だけ書く。開発ログが無いときは報告書に「記録なし」と書く(採点には影響しない)。
理由: 1 行の単位が決まっておらず、凍結後の記録場所が無かった。

C-35(8 節) 案: 表に足す。

  • 第三者が確かめられること: 「付くのが発走後になった日は除く。ノード無しの verify はブロックエクスプローラを信じる前提」。
  • 記録と主催エージェントの確認に頼ること: 「そのレースのオッズ・人気の数字が無いこと」「共通の入力をそのまま使ったこと(ハッシュの一致)」「記録の書き換えが無いこと(git の履歴)」。
  • 自己申告: 「LLM に Web 検索・メモリーを使わせていないこと」「LLM の返事が凍結したプロンプトとモデルから出たこと」「人が予想・入力ファイルに手を入れていないこと」「学習データに他人の予想・指数と 11/8 より後の結果が入っていないこと」「読めない形式で保存した入力にオッズ・人気が無いこと」「主催が共通の入力を push してから自分の予想を始めたこと」。
  • 表の下に「報告書は 2 人の経験を並べ、問いへの答えは『この経験の 2 人が』と限って書く。到達率は罰なしの log loss で出し、罰を含む勝敗と並べる。裁定の一覧とその影響も載せる。」

理由: 「確かめきれない部分は自己申告」(前提)の中身をここに並べる。
