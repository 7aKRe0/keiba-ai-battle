決めたこと(ルールに無いので道具の側で決めた。変えるならルールか裁定で):
- 結果ファイルの書式: 1 行 1 レース、`race_id,1着,取消除外,単勝オッズ,出典`。単勝オッズは `馬番:オッズ` を空白区切りで全出走馬。出走頭数は単勝オッズの頭数(取消除外を除く)。
- 置き場所: 凍結の一覧 `hashes/20261111_凍結_名前.txt`、締切後の CSV と入力 `提出/YYYYMMDD_名前/`、結果 `結果/結果.csv`。
- 乱数: SplitMix64 を `score.py` の中に実装、種 20261114。区間はパーセンタイル法(線形補間)。Python や numpy の版で数字が変わらないようにするため、numpy も使っていない。

## 動かして確かめたこと(クラウドの Linux、Python 3.13)

| B | 0.828635 | 0.912279 | [0.000000, 3.726507] |

| 市場(物差し) | 0.799298 | 1 | - |

- 勝ち(log loss が小さい方): B

手計算は `tests/手計算.md`(分数までは手、ln だけ電卓)。

- 架空の 216 レース × 2 人で `score.py` が 1.3 秒で終わる。
- `--format-only` は、race_id の日付がファイル名と違う CSV をエラーで止める。
- `compare.py`: 同じ CSV → 一致。1 頭だけ 0.0000011 ずらす → 不一致。
- `hashes.py`: 作った一覧が `sha256sum -c` でも OK。ファイルを 1 つ書き換え・1 つ足すと「不一致」「一覧に無い」で終了コード 1。
- `push_times.py`: 本物の GitHub ではなく、決まった JSON を返す偽の `gh` で確かめた。`log` は 2 回目に 0 件(重複して書かない)。`submission` は締切 21:00 ちょうどの push を外し、20:59:59 の push の時点のファイルの SHA-256 を出し、ファイルを変えた push と actor を並べた。push 以外の種類(branch_creation)は除いた。
- `ots.py`:
  - `stamp`: 失敗。この環境のネットワークの方針で、OpenTimestamps のカレンダー(a.pool.opentimestamps.org など)への接続が 403 で拒まれた。
  - `verify`: OpenTimestamps の公式の例 `hello-world.txt.ots`(Bitcoin のブロック 358391 で完結済み)で、ノード無しの段 1 は通った。`To verify manually, check that Bitcoin block 358391 has merkleroot 8a1b66ec…7e00` まで出る。中身を変えたファイルでは `File does not match original!` で止まる。段 2(エクスプローラとの比較)は、blockstream.info と mempool.space への接続が 403 で拒まれ、「未確認」と出て終了コード 1。

## 未検証のこと

- **OpenTimestamps の最後まで(Bitcoin のノード無しの verify)はクラウドで通らなかった。** stamp・upgrade は未検証、verify は「ファイル → merkle root」までは確認済み、「その merkle root が本当にブロック 358391 のものか」は未検証。
  - 代わりの確かめ方: ネットワークの通る PC で `python tools/ots.py verify hello-world.txt.ots` を実行し、2 つのエクスプローラで「一致」と出るかを見る。出なければ、ブラウザで `https://blockstream.info/block-height/358391` を開き、Merkle root が `8a1b66ecb7cbd07d8139a7e7d7f2c41aab1f5009b8364aaf61d03ad245e47e00` か目で比べる(エクスプローラの表示とバイトの並びが同じかも、ここで確かめる)。
  - クラウドで通すなら、環境のネットワーク設定で `*.pool.opentimestamps.org`・`a.pool.eternitywall.com`・`ots.btc.catallaxy.com`・`blockstream.info`・`mempool.space` を許可する。
- Windows での動作すべて(本人の側で確認する)。日本語のファイル名、`pip install opentimestamps-client`、`gh` の実行。
- `gh api repos/{owner}/{repo}/activity` を本物のリポジトリに対して叩いていない。返る項目(timestamp・actor・before・after・activity_type)、force push が残るか、記録がいつまで残るかは未確認。早めに一度 `python tools/push_times.py log` を実行して確かめる。

## ルールとの食い違い・穴

文書は直していない。直すかどうかは 2 人で決める。

1. **見出しの版が古い。** `ルール.md` の見出しは「第 2 版」だが、変更履歴は第 3 版まである。
2. **開催日の表が空。** 1 節の表が「(確認中)」のまま。開発開始前に書く、とルールにある。
3. **評価期間中の結果が入力ファイルに入る。** 2 節は「評価期間中に確定したレースの結果は、あとのレースの入力にも使わない」。ところが 11/21 以降の出馬表には、ふつう前走(11/14〜の評価期間のレース)の着順やオッズ・人気が載る。2 節の「入力は締切時点で手に入る情報なら何でも」と、この禁止が食い違う。作り直しの確認(4 節)が探すのは「そのレースのオッズ・人気」だけなので、これも見つからない。
4. **凍結したコードを主催エージェントに渡す時期・方法が無い。** 4 節の作り直しには相手の凍結コード・モデル・成績データが要るが、いつ・どこに・どう渡すかが書かれていない。主催エージェントは本人の PC で動くので、本人の提出を本人の側で作り直すことになる(利害が重なる)。友人の側でも同じエージェントで作り直すか、を決めていない。
5. **作り直しの環境が決まっていない。** 凍結するのは「ライブラリの版の一覧」だけで、OS・Python の版・CPU か GPU かは無い。環境が違うと 0.000001 を超える差が出得て、その日は全馬同じ確率で採点になる。
6. **締切ちょうどの扱いが無い。** 「23:59」「21:00」をちょうど含むか。道具は `--deadline` の時刻より前(`<`)を締切前とした。主催エージェントには、最初の確認で裁定するよう書いた。
7. **置き場所が無い。** 締切後に push する CSV と入力ファイルの場所、凍結の一覧のファイル名、結果ファイルの書式。道具の側で仮に決めた(上の「決めたこと」)。締切後に CSV と入力をいつまでに push するかの期限も無い。
8. **他人のファイルを書き換えられる。** 共有リポジトリなので、相手の `hashes/` のファイルも push で変えられる。`push_times.py` は「ファイルを変えた push の actor」を出すが、ルールに「自分のファイルだけを変える」が無く、名前と GitHub のログイン名の対応も無い。主催エージェントは `記録/参加者.md` を見るとした(まだ無い。2 人で書く)。ブランチ保護も未設定(未確認)。
9. **時刻証明を誰がいつ付けるか。** 4 節は「1 回付ける」だけ。発走前に付ける必要がある(土曜の第 1 レースは朝)。主催エージェントの手順では締切の直後に付ける。
10. **採点の細則の残り。**
    - 確率の合計が 0(全部 0 で、CSV に無い出走馬もいない)、負の値、数でない値の扱いが無い。`score.py` はエラーで止める(裁定が要る)。
    - CSV にあって、出走馬にも取消除外にもいない馬番の扱いが無い。`score.py` は外して注意を出す。
    - 0.001 の下限と処理の順番を物差し 2 つにも当てるかが無い。`score.py` は同じ処理を当てた。市場は大穴(例 999.9 倍)が勝つと下限が効き、市場が少し有利になる。
    - 乱数の種の値・生成器・区間の求め方が無い。第三者が区間を再計算するにはスクリプトの定めに頼ることになる。
    - 「出走頭数」は取消除外を除いた頭数と解釈した。
    - UTF-8 の BOM(Excel が付ける)を許すか。`score.py` は許した。
11. **オッズ・人気の確認は機械だけでは決まらない。** 入力に過去のレースのオッズ・人気(使ってよい)が入っていると、`grep` の当たりから「そのレースのもの」を見分けるのは読んで判断することになる。
12. **ノード無しの verify はエクスプローラを信じることになる。** 8 節は時刻証明を「第三者が自分で確かめられること」に入れているが、ノードを持たない第三者はエクスプローラを信じることになる。2 か所と比べるようにしたが、報告書ではこの前提を書いた方がよい。
13. **おまけの頭数。** 6 節は「8 頭以上のレースから選ぶ」だが、取消・除外で 7 頭以下になると複勝は 2 着までになる。その場合の扱いが無い。
14. **結果パックの中身と採点の入力の差(小)。** 趣旨の結果パックは「race_id・1 着の馬番・最終単勝オッズ・リンク」。`score.py` は取消除外の列も読むが、取消除外の馬は単勝オッズに載らないので、この列が空でも点数は同じになる。
15. **記録の書き足しだけ、は指示で守るだけ。** 主催エージェントの Write は上書きができる。手順で「既にあるファイルは追記だけ」と書いたが、仕組みでは防いでいない。git の履歴で後から確かめられる。
