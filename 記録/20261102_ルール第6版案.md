## 2. 使えるデータ

- 学習・調整に使えるのは、11/8(日)までに確定したレースのデータだけ(凍結後はモデルに手を加えないため)。予想の入力には、評価期間中に確定したレースの結果(前走の着順・オッズなど)も、締切の時点で公開されていれば使ってよい。確定していないレース(審議中など)の結果は使わない。新しい結果は入力ファイルとして保存する。
- 予想の入力には、締切の時点で手に入る情報なら何を使ってもよい(出馬表、天気予報、金曜時点の馬場状態、過去のレースのオッズ・人気など)。何を知っていて何を使うかの差も勝負のうち(2026-11-02 本人決定)。
- ただし、次のものは使わない。問いの物差しを壊すため。
  - そのレースのオッズ・人気(使うと市場の予想をなぞることになり、市場との比較が意味を失う)。単勝以外の券種、途中のオッズ、新聞やサイトの想定オッズ・想定人気、海外のものも含む。過去のレースのオッズ・人気は使ってよい。
  - 他人の予想(印など)。人や予想サービス(新聞・予想サイト・AI 予想サービスなど)が出した予想のこと。データ提供元が出す予想・指数・印(JRA-VAN のマイニング予想、netkeiba の予想印・指数など。有無は未確認)も含み、学習データにも入れない。自分で組んだ仕組みの中の LLM の出力と、過去の結果から自分で計算した特徴は含まない。
- 外から取ってくるもの(出馬表、天気、外部 API や LLM の返事など)は、締切前にファイルに保存して「入力ファイル」とする。そのレースのオッズ・人気・印の欄は取得の時点で落とす(ページ全体の保存は避けることを勧める。含まれていれば 4 節の確認に当たる)。取ってきたものは加工せずに保存する(欄を落とす以外に中身を書き足さない)。LLM に渡した文と返事は、取ってきたものとは別フォルダに置く。作り直しの確認で読めない形式(parquet など)で保存すると、オッズ・人気の確認ができず、その項目は 8 節の自己申告の区分になる。凍結したコマンドは入力ファイルだけを読み、入力ファイルが欠けていたら取りに行かずに止まる(または、そのレースを出さない)。
- 予想に LLM を使ってよい(ローカル・クラウドとも)。予想を出すときの LLM に渡してよいのは、入力ファイルと凍結したもの(プロンプト・例・11/8 までの成績データの写し)だけ。Web 検索・メモリーは切る。渡した文(リクエスト全体。モデル名・設定を含む)と返事は、呼んだ分を全部、入力ファイルとして保存する。呼ぶ回数と返事の選び方(平均など)はコードで決める(通信・形式の失敗の再実行はよい)。人が返事を選ばない・直さない。LLM が使えなかったときに LLM 抜きで出す道を持つことと、返事に倍率・人気順位の数字を書かせない作りにすることを勧める。
- 締切後の騎手変更・斤量変更は予想に反映しない。
- データの取り方は自由。JRA-VAN Data Lab の 1 か月無料お試し(1 回限り)を使う場合は、11/29 まで届くように申し込む日に注意する。JRA-VAN のデータを LLM に渡すこと・写しを相手に渡すことが規約で許されるかは各自で確かめる(未確認)。
- 11/4 より前から持っているコード・データ・学習済みモデルは使ってよい。開発ログの「経験」に種類と量を書く。

- 置いたものは書き換えない。直すときは `YYYYMMDD_v2.csv` のように別名で足す。締切後は直しを置かない。どれを使ったかはハッシュで分かる。作り直し(4 節)には締切前に置かれた最新の版を使う。

## 3. モデル凍結(11/11 23:59)

- 凍結するもの: 予測コード(出馬表の取得・加工を含む)、学習済みモデル、11/8 までの成績データの写し、ライブラリの版の一覧、環境の申告(OS・Python の版・CPU か GPU か)、開発ログ。LLM を使う人は、プロンプト・例・版つきのモデル名・設定(温度など)・呼び出しのコードも凍結する。API の鍵は凍結に入れない。LLM の呼び出しそのものの再現は求めない(返事を保存するため)。
- 予測は 2 段に分けてよい。前の段は、入力ファイルを取ってきて保存する(出馬表の取得、LLM の呼び出しと返事の保存)。後の段は、入力ファイルだけから CSV を作る決まったコマンド 1 つ(例: `python predict.py <入力ファイルのフォルダ>`)。入力ファイル以外の引数・設定の切り替えは受け付けない作りにし、乱数の種を固定する。両方の段のコードを凍結に含め、作り直しの対象は後の段。環境が違っても 0.000001 を超える差が出ない作り(CPU で推論、種を固定)にするのは参加者の責任。
- 凍結するファイル一式のハッシュの一覧(`hashes/20261111_凍結_名前.txt`)を `python tools/hashes.py make` で作り、締切前に共有リポジトリに push する。一覧に入れるのは自分が指定したファイルだけで、実行で増えるファイル(`__pycache__`・`.venv`・`.git` など)は見ない。一覧に無いコード・モデル・データは作り直しで使えない。主催エージェントは、GitHub に記録された push の時刻を取得して記録する。一覧には OpenTimestamps の時刻証明を付ける(`.ots` は一覧と同じ場所に置く)。
- 凍結の一覧が 11/11 23:59:59 までに無ければ、11/13(金)21:00 までの `hashes/20261111_凍結_名前.txt` の最初の push を凍結とみなし、遅れを記録と報告書に書く。それも無ければ、その参加者の提出は全日 全馬同じ確率(4 節の罰つき)。
- これ以降、凍結したものに手を加えない。評価期間にやるのは、入力ファイルを取ってきて、凍結したコマンドで予測を出すことだけ。例外は 2 つ。(1) 取得先のページや API の形が変わって読めなくなったときだけ、読む部分を直してよい。出力の列と中身の定義は変えない。直した版は、凍結したファイルを書き換えずに新しいファイルとしてその日の締切前に push し、理由を書く。予測の部分(モデル・プロンプト・設定・後処理)は変えない。(2) 提出の手順を自動にする補助(ハッシュ作成・push・定時実行など、予測の中身に触れないもの)は作ってよい。
- 予測が途中で落ちた日は、出せたレースまでの CSV を出す。コードを直して出し直さない(CSV に無いレースは全馬同じ確率で採点される。4 節)。

## 4. 予想の提出(各開催日の前日 21:00 締切)

- その日の入力ファイルを保存し、凍結したコマンドで、その日の全レースの CSV を 1 本出す。定時に自動で動かして出してよい。
- 締切までに、CSV と入力ファイル全部のハッシュを書いたファイル(`hashes/YYYYMMDD_名前.txt`。`python tools/hashes.py make` で作る)を、共有リポジトリの main に push する。ハッシュだけなので、相手に予想の中身は見えない。締切前の最後の push を正式な提出とし、主催エージェントが GitHub に記録された push の時刻を取得して記録する。締切前なら何度 push してもよい(早く最初の版を出しておく。20:50 までを目標にする。push が拒まれたら `git pull --rebase` して再 push する)。
- 自分の名前のファイル以外を変えない。相手の名前のファイルを変えた push は、その版を提出とみなさず、持ち主の最後の版を提出とする。変えた側のその日の提出は無効。名前と GitHub のログイン名、ルールの版を読んだ日付は `記録/参加者.md` に 11/4 までに 2 人で書く。
- CSV と入力ファイルは、締切後、その開催日の最初の発走の前までに `提出/YYYYMMDD_名前/`(CSV は `YYYYMMDD_名前.csv`、入力ファイルは `入力/` の下)に push する。ハッシュが提出したものと一致しなければ、その日の提出は無効。発走までに push が無い日は出し忘れの扱い。締切前に CSV や入力ファイルを push しない。してしまったら記録し、相手の CSV は 2 節の「他人の予想」として扱う(読んで使えば違反。自己申告)。
- その日の 2 人のハッシュのファイルに、主催エージェントが締切から 3 時間以内(目標 1 時間以内)、遅くともその日の最初の発走の前に OpenTimestamps の時刻証明を 1 回付ける(発走時刻は未確認)。どちらの参加者が実行してもよい。`.ots` はハッシュのファイルと同じ場所に置く。発走前は保留の `.ots` でよい。付けるのが発走後になった日は時刻を記録し、報告書ではその日の「発走前に存在したこと」を push の時刻の区分(8 節)に移す。時刻証明が示すのは「発走前に存在したこと」までで、分単位の締切の証明には使わない(締切は GitHub の push の時刻で判定する)。
- 形式: UTF-8(BOM は許す)、見出し行 `race_id,馬番,確率`。race_id は共通の入力のもの(`YYYYMMDD-場名-R`、例: `20261114-東京-11`)。確率は小数 8 桁以上で書く(桁が足りないのは形式の誤りとしない。作り直しの不一致になる危険は自分の責任)。ファイル名は `YYYYMMDD_名前.csv`。
- 人の手を入れない(2026-11-02 本人決定): 予想を出す途中と提出後に、人が予想に手を入れない。同じコマンドの再実行と、取れなかったページの取り直しはよい。出た確率の数字、予測コード、モデル、設定、プロンプトを人が書き換えない。入力ファイルを手で直すのは、取得の失敗を補うとき(欠けた欄の取り直しなど)だけで、予想の材料を書き足さない。直したら評価期間のログ(7 節)に 1 行書く。
- 作り直しの確認: 主催エージェントが、凍結したコードとデータに提出した入力ファイルを入れて全開催日の CSV を作り直す。作り直しは、凍結の一覧にあるファイルと入力ファイルだけを置いた空のフォルダで、申告した環境で行う。Python とライブラリは、凍結した版の一覧と環境の申告にしたがって主催が入れる。一覧に無いコード・モデル・データが要って動かなければ作り直せない扱い。主催側で環境がそろわないときは、その参加者が自分の PC で同じ道具(`tools/`)を動かし、出力と環境を `記録/` に push する。全馬の確率の差が 0.000001 以内なら一致とする。一致しない日は、その日の提出を全馬同じ確率で採点する(罰なし)。共通の入力に原因がある不一致は、参加者の不利にしない。
- オッズ・人気の確認: あわせて、入力ファイルにそのレースのオッズ・人気の数字(倍率・人気の順位)が入っていないかを確かめる。出どころ(LLM の返事を含む)は問わない。そのレースのものかどうかは、入力ファイルの中でその race_id・馬名と同じ行(同じ表)にある倍率・順位の数字で見分け、判断と根拠を裁定に書く。入っていた日は、その日の提出を全馬同じ確率で採点する(罰なし)。
- 凍結物の受け渡し: 作り直しに要る凍結物(予測が読むものだけ。一覧にあるもの)は、最後の締切(11/28(土)21:00)の後〜11/30(月)までに、共有リポジトリの非公開の release に zip で置く。ハッシュは凍結のものと同じ。JRA-VAN のデータの写しは規約が許す範囲だけ渡し(未確認)、渡せないときは上の「参加者が自分の PC で動かす」形にする。済んだら主催は消し、結果パックに入れない。
- 出し忘れ・無効: 主催エージェントが、凍結したコードと、締切までに置かれた共通の入力だけで作り直した CSV で採点する。参加者が後から出した入力ファイルは使わない。作り直せないときは全馬同じ確率で採点する。出し忘れは記録し、件数を報告書に書く。
- 罰: 作り直せなくて日全体を全馬同じ確率で採点する場合と、凍結の一覧が無い場合は、1 レースあたり 0.1 を log loss に足す(出さない方が得にならないようにするため)。作り直しの不一致・オッズや人気の混入・形式の誤りには足さない。罰は 2 人の勝敗(log loss の比較)にだけ使う。到達率と報告書の問いへの答えは罰なしの log loss で出し、罰の有無を両方載せる。
- 形式の誤りは直さない。CSV に無いレースと、形式の違う行(数でない・負・空・同じ馬が 2 行)を含むレースは、そのレースだけ全馬同じ確率で採点する(日全体は無効にしない)。見出し行・ファイル名・文字コードの誤りは、その日を全馬同じ確率で採点する(罰なし)。

## 5. 採点

- 対象: 評価期間の全レース。レースの中止・開催の中止は採点から外す(平均の分母からも外す)。代替競馬は対象外。順延・開催変更になったレースは、元の日付の race_id と元の締切のまま採点する。中止が締切後に決まった日は、提出済みの CSV と入力の push だけ行い、採点しない。
- 着順は確定着順(降着・失格を反映)。出走取消・発走除外の馬は外す。競走中止の馬は残す。
- 処理の順番: 取消・除外の馬を外す → CSV に無い出走馬に 0.001 を付ける → 合計が 1 になるように直す → 勝った馬の確率 p を取る(同着は足す) → p が 0.001 未満なら 0.001 にする。
- 細則: 確率の合計が 0 のレースは全馬同じ確率。出走馬にない馬番の行は無視する。出走頭数は取消・除外を除いた頭数。下限 0.001 と処理の順番は物差し 2 つにも同じに当てる。ブートストラップの乱数(生成器・種)と区間の求め方は `tools/score.py` の定めに従う。race_id・馬番の表記は共通の入力を正とし、結果と合わないレースは CSV に無いものとして扱う。
- log loss: 全レースの −ln(p) の平均。**小さい方が勝ち。** 勝敗は平均の大小で決める(4 節の罰を含む)。
- 差の 95% 区間を、レース単位のペアのブートストラップ(10,000 回、乱数の種を固定)で出して並べる。区間が 0 をまたぐときも勝敗は平均で決め、報告書に「偶然と区別できない差」と書く。
- 物差し:
  - 全馬同じ確率: 1 ÷ 出走頭数。
  - 市場の予想: JRA 公式の最終単勝オッズから、1/オッズ を出走馬で足して 1 に直したもの。最終オッズは締切後の情報(馬体重・馬場など)を含むので、同じ条件の相手ではなく「上限の目安」として扱う。
- 全頭の最終単勝オッズが取れなかったレースは、3 つとも採点から外し、件数を報告書に書く(中止と同じ扱い)。
- 問いへの答え: 到達率 =(全馬同じ確率の log loss − モデルの log loss)÷(全馬同じ確率の log loss − 市場の log loss)。0 なら何も考えない予想と同じ、1 なら市場と同じ。罰なしの log loss で出し、ブートストラップの区間つきで報告する。
- 結果とオッズの正本は JRA 公式の成績ページ。`結果/結果.csv`(1 行 1 レース、`race_id,1着,取消除外,単勝オッズ,出典`)は、保存したページ(`結果/原本/`)からスクリプトで作り、転記はしない。スクリプトで作れないレースは、2 人がそれぞれ同じ原本から作って突き合わせ、違いがあれば記録する。保存したページとスクリプトは共有リポジトリに置き、2 人とも同じ出力が出ることを確かめられるようにする。件数は 1 節の表と突き合わせる。結果パックには race_id・1 着の馬番・最終単勝オッズと出典のリンクだけを入れる(JRA-VAN のデータは配り直さない)。

## 6. おまけ: 人間代表との 1 レース

- 対象レースと予備のレース(中止のとき用)を、11/11 までに決めて記録する。8 頭以上のレースから選ぶ。取消・除外で 7 頭以下になったときは予備に替える。予備も 7 頭以下なら、そのまま行い複勝は 2 着まで。
- モデルの印は、提出した CSV の確率の上位 3 頭(◎○▲ の順)。確率が同じなら馬番の若い方。
- 人間代表は、発走前までに印を出す(push の時刻で確かめる)。発走前に無ければ不参加とする。何を見てもよい(エンタメ枠のため)。
- 点数: ◎ が 1 着なら 3 点。さらに、印の馬(◎ を含む)が 3 着以内に入るごとに 1 点。例: ◎ が 1 着、▲ が 3 着 → 3 + 1 + 1 = 5 点。同点なら馬券の収支で決める。
- 馬券: 3 者とも ◎ の単勝と複勝を 100 円ずつ。本人と友人がまとめて買う。◎ が取消・除外になったら、その馬券は返還扱いにして、印は繰り上げる。
- 1 レースなので、問いへの答えには使わない。

## 7. 開発ログ(AI の使い方の記録)

- 開発開始時に、経験(プログラミング・機械学習・競馬)と、11/4 より前から持っているコード・データ・モデルの種類と量を書く。
- AI を使った作業ごとに 1 行ずつ、`開発ログ_ひな形.md` の形で記録する。1 行は「AI に頼んだ 1 つのまとまり」(同じ試行の繰り返しは 1 行にまとめて回数を書く)。プロンプトの原文は要らない。頼み方と結果は、ひな形の選択肢から選ぶ。
- 毎日の終わりに、その日の作業時間の合計を書いて push する(目標。遅れても凍結までにそろえばよい)。
- 凍結(11/11)のときに、ハッシュの一覧に含める。採点には使わず、報告書で「AI の手を借りてどう作ったか」を回数と時間の集計で示すために使う。
- 凍結後の AI の利用(入力の取得・提出の運用・手で入力ファイルを直したこと)は、凍結の一覧の外の `開発ログ_評価期間_名前.md` に、日ごとの合計と 1 行の注記だけ書く。
- 開発ログが無い・凍結の一覧に無いときは、報告書に「記録なし」と書く(採点には影響しない)。

## 8. 報告書での書き分け

報告書では、主張を次の 3 つに分けて書く。「不正がないことを証明した」とは書かず、何を確かめれば否定できるかを書く。

| 区分 | 中身 |
|---|---|
| 第三者が自分で確かめられること | 点数(結果パックで再計算できる)、公開した CSV が提出のハッシュと一致すること、発走前に存在したこと(時刻証明。付くのが発走後になった日は除く。ノード無しの verify はブロックエクスプローラを信じる前提) |
| 非公開リポジトリの記録と主催エージェントの確認に頼ること | 締切前に出したこと(GitHub の push の時刻)、凍結したモデルの出力であること(作り直しの確認)、入力ファイルにそのレースのオッズ・人気の数字が無いこと、共通の入力をそのまま使ったこと(ハッシュの一致)、記録の書き換えが無いこと(git の履歴) |
| 自己申告 | 開発期間、経験、AI の使い方、入力ファイル以外から情報を持ち込んでいないこと、LLM に Web 検索・メモリーを使わせていないこと、LLM の返事が凍結したプロンプトとモデルから出たこと、人が予想・入力ファイルに手を入れていないこと、学習データに他人の予想・指数と 11/8 より後の結果が入っていないこと、読めない形式で保存した入力にオッズ・人気が無いこと、主催が共通の入力を push してから自分の予想を始めたこと |

報告書は 2 人の経験を並べ、問いへの答えは「この経験の 2 人が」と限って書く。到達率は罰なしの log loss で出し、罰を含む勝敗と並べる。裁定の一覧とその影響も載せる。
